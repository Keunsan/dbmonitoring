## 1. 한 줄 정의

여러 업무 시스템의 데이터베이스를 **한곳에서 상시 관제**하여 **운영 연속성**을 지키고, 시스템별 **화면·로직 개발·배포** 업무와 **병행**할 수 있게 하는 **통합 데이터베이스 관제 플랫폼**.

---

## 2. 왜 만드는가 (추진 동기)

### 2.1 담당자가 겪는 현실

- **여러 업무 시스템**을 동시에 운영·개발한다.
- **시스템별** 화면·로직 개발·수정·배포가 주된 업무지만, 각 시스템의 **DB 안정성**이 무너지면 **전체 서비스 연속성**이 깨진다.
- DBMS·인스턴스마다 **도구와 관측 경로가 달라** “지금 조직 전체 DB가 안전한가?”에 **빠르게** 답하기 어렵다.

### 2.2 관제 없을 때의 리스크

| 상황 | 리스크 |
|------|--------|
| 개발·배포·배치 집중 | CPU·Blocking·Long Query 누적을 **늦게** 인지 |
| 장애 의심 | 세션·Wait·Deadlock을 **한 화면**에서 추적하기 어려움 |
| 성능 이슈 | SQL·실행 계획 이력이 **시스템별로 분산** |
| 대응 | 알림·점검 **절차·우선순위**가 사람마다 다름 |

### 2.3 이 시스템이 채우려는 자리

**성능 분석 전용 툴**이 아니라, 다수 시스템 DB를 **업무 시스템 단위로 묶어** 상시 모니터링하고 이상 징후를 **조기에** 알리는 **관제 허브**.

---

## 3. 목적 (무엇을 달성하는가)

| # | 목적 | 설명 |
|---|------|------|
| 1 | **통합 관제** | 이기종 DB(MSSQL, Oracle, Azure SQL 등)를 **단일 포털**에서 상태 파악 |
| 2 | **상시 모니터링** | 아침·퇴근 등 **정해진 점검 루틴에 의존하지 않고**, Collector·화면·알림으로 **항상** 상태를 추적 |
| 3 | **즉각 인지** | **사용자 장애로 이어질 수 있는** DB 이상(부하·Lock·Blocking 등)을 운영자가 **지연 없이** 인지 |
| 4 | **표준화** | 동일 메뉴·지표·알림 언어로 DBA·운영자·개발자가 **같은 그림**을 봄 |
| 5 | **개발·운영 병행** | 앱 개발에 치중하는 동안에도 DB 안정성을 **자동 수집·알림**으로 별도 라인 유지 |

### 3.1 운영 방식: 루틴 점검 없이 상시 관제

| 하지 않는 것 | 하는 것 |
|--------------|---------|
| 아침 점검·퇴근 전 점검 등 **고정된 수동 루틴**을 전제로 하지 않음 | **자동 수집** + **대시보드·실시간 화면** + **임계치·이벤트 알림**으로 상시 관제 |
| “나중에 한번 본다”에 의존 | **이상 발생 시** (및 평시에도 화면을 열어 두었을 때) **즉시** 상태·원인 후보 파악 |

운영자는 다른 개발·운영 업무를 하면서도, **사용자 체감 장애로 이어질 징후**가 생기면 **알림 또는 실시간 UI**로 바로 알 수 있어야 한다.

### 3.2 사용자 영향 관점의 관제 대상 (핵심)

**시스템 사용자**가 업무 화면·API 사용 시 느끼는 장애·지연·오류와 연결될 수 있는 DB 측 요소를 상시 추적한다.

| 분류 | 대표 징후 | 운영자가 알아야 하는 이유 |
|------|-----------|---------------------------|
| **부하·용량** | CPU·메모리·I/O·Log/Temp·연결 수가 **임계치 초과** | 응답 지연·타임아웃·전체 느려짐 |
| **Lock·대기** | **LOCK**, Blocking, 장시간 Wait, 교착(Deadlock) | 특정 기능 멈춤·무한 대기·오류 |
| **세션·쿼리** | Long-running session/query, 급증한 active session | 화면 정지·배치·동시 사용자 피해 |
| **가용성** | DB 연결 실패, **수집 실패** (DB 다운·네트워크 의심) | 서비스 불능·블라인드 구간 발생 |
| **성능 급변** | Top SQL·실행 계획 변경·성능 회귀 (2차 분석) | 특정 메뉴·배치만 간헐적 장애 |

임계치 정책·알림 엔진은 위 요소를 **사용자 영향 가능성** 기준으로 설정·확장한다.

### 3.3 성공 상태 (운영자 관점)

1. **어느 업무 시스템·DB**에서 이상이 발생했는지 **상시 추적**되고, 이상은 **포털 화면**(대시보드·실시간·알림 화면)으로 인지한다. (외부 알림은 §5.1)  
2. 인지 후 **Blocking·세션·지표·SQL** 등으로 **원인 후보**를 같은 포털에서 좁힐 수 있다.  
3. 고정 점검 시간 없이도, **평시 + 이벤트 발생 시** 동일한 관제 흐름이 유지된다.

## 5. 상시 관제·이벤트 유형 (루틴 아님)

고정 **점검 시나리오** 대신, 아래 **이벤트/상태**가 **항상** 수집·**화면에 표시**된다.

### 5.1 P0 확정 — 인지 방식·주기

| 항목 | 확정 (2026-05-26) |
|------|-------------------|
| **외부 알림** | **미사용**. Teams·메일·SMS 등은 검토 후 **별도 요청 시** 추가한다. |
| **인지 수단** | **포털 화면만** — 통합/실시간 대시보드, Blocking·세션 등 모니터링 메뉴, **알림 화면**(앱 내 이벤트 목록·임계치 표시). |
| **Collector 수집 주기** | 인스턴스 기본 **60초(1분)**. (등록·신규·미설정 시 기준) |
| **화면 갱신 주기** | 주요 실시간·대시보드 UI polling **60초(1분)** (수집 주기와 동일). |

TO-BE 리팩토링 후에도 위 수치·정책을 **기본값**으로 유지한다 (변경 시 본 절·DEC 갱신).

### 5.2 이벤트 유형별 매핑

| ID | 유형 | 화면 인지 (1차) | 외부 알림 | 연결 기능 |
|----|------|-----------------|-----------|-----------|
| E-01 | 임계치 초과 | ○ 대시보드·실시간·**알림 화면** | ✗ 보류 | 임계치 정책, `alerts/evaluate`, summary |
| E-02 | Lock·Blocking | ○ blocking·세션 | ✗ 보류 | `monitoring/blocking`, sessions |
| E-03 | Wait·교착 | ○ waits·deadlocks | ✗ 보류 | 해당 모니터링 API·화면 |
| E-04 | 세션·Long Query | ○ sessions·Top SQL | ✗ 보류 | sessions, `monitoring/sql` |
| E-05 | 수집·연결 이상 | ○ 인스턴스 관리·상태·알림 화면 | ✗ 보류 | collector/status, COLLECT_FAILED (화면) |
| E-06 | 성능 급변 | ○ 분석 메뉴 | ✗ 보류 | plan-changes, regressions, Top SQL |

**참고**: `alerts/evaluate`는 **앱 내 알림 이벤트 생성**용으로 유지할 수 있다. 이는 “외부 발송”이 아니라 **화면(알림 live/history)** 에 노출하기 위한 경로다.
